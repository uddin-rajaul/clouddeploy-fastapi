# Deployment Journal

## 2026-08-13 — First Successful Production Deployment

Today I finished the actual deployment path instead of just testing whether GitHub Actions could reach the EC2 instance.

The first thing I changed was the way EC2 accesses the private GitHub repository. Previously the repository was using HTTPS, which meant GitHub was asking for a username and password/token when the server tried to fetch changes.

I did not want the production server depending on my personal GitHub credentials, so I switched the repository remote on EC2 to SSH.

A dedicated deploy key was created for the EC2 instance and added to the GitHub repository. After changing the remote, the server was able to fetch from GitHub without asking for a username or password.

The remote is now:

```text
git@github.com:uddin-rajaul/clouddeploy-fastapi.git
````

This gives the EC2 instance its own identity for accessing the private repository instead of using my personal GitHub authentication.

### Deployment workflow

With GitHub access from EC2 sorted out, I created the first real production deployment workflow.

The deployment flow is:

```text
git push
   |
   v
GitHub Actions
   |
   | AWS OIDC
   v
AWS IAM deployment role
   |
   | SSM SendCommand
   v
EC2
   |
   +-- git fetch origin main
   +-- checkout exact commit
   +-- uv sync --locked
   +-- alembic upgrade head
   +-- restart systemd service
   +-- verify service
   +-- verify HTTP endpoint
```

For the first deployment, I kept the workflow manually triggered with `workflow_dispatch`. I wanted to prove the deployment process before allowing every push to `main` to deploy automatically.

### First deployment problem

The first deployment reached EC2 successfully but failed here:

```text
sudo: uv: command not found
```

The important part was that `uv` was installed for `ec2-user`, but SSM was executing the command with a different environment and PATH.

The deployment was already running Git commands as `ec2-user`, but `sudo -u ec2-user uv ...` could not find the `uv` executable.

Instead of changing the server-wide PATH just to make the deployment work, I used the explicit path to the existing installation:

```text
/home/ec2-user/.local/bin/uv
```

The deployment commands therefore use the absolute path for `uv`.

This was a useful distinction: the problem was not that `uv` was missing. It was a PATH/environment problem caused by running the command non-interactively through SSM.

### Deployment verification

After fixing the `uv` path, the deployment succeeded.

The successful deployment checked out this exact commit:

```text
732d7621db476f43384537bffa0e3c950bf49a3f
```

The deployment successfully completed:

```text
git fetch
git checkout
uv sync --locked
alembic upgrade head
systemd restart
systemd active check
HTTP health check
```

The application responded with:

```json
{"message":"Welcome to CloudDeploy API"}
```

The SSM command returned:

```text
Deployment status: Success
```

This is the first point where the complete production deployment path has been proven rather than just configured.

### Deployment failure visibility

One change I kept in the deployment workflow was making sure SSM failures do not hide the actual command output.

Initially, this:

```text
aws ssm wait command-executed
```

stopped the GitHub Actions job immediately when the remote command failed.

That meant the workflow showed only that the command failed, without showing the useful error from EC2.

The workflow was changed so that the SSM result is retrieved even when the command fails. This allows both standard output and standard error to be shown before the GitHub Actions job is marked as failed.

That made the `uv: command not found` problem easy to identify.

### Switching to automatic deployment

After the manual deployment succeeded, I changed the workflow from:

```yaml
on:
  workflow_dispatch:
```

to deploying on pushes to the main branch.

The resulting flow is now:

```text
git push origin main
        |
        v
GitHub Actions
        |
        +-- CI
        |
        +-- AWS OIDC
        |
        +-- SSM deployment
        |
        v
EC2 production
        |
        +-- checkout pushed commit
        +-- sync dependencies
        +-- run migrations
        +-- restart application
        +-- health check
```

I then tested the actual automatic deployment flow, and it worked.

This means the project now has a real CI/CD path rather than a manually operated deployment process.

### Current architecture

The production setup now looks like:

```text
GitHub
  |
  | push to main
  v
GitHub Actions
  |
  | tests
  |
  | OIDC
  v
AWS IAM
  |
  | SSM
  v

  +-- private GitHub repo via dedicated SSH deploy key
  +-- FastAPI application
  +-- systemd
  |
  v
```

The application itself continues to run through systemd as:

```text
User=ec2-user
```

The SSM command may execute with elevated privileges, but the FastAPI service is not running as root.

### What is now proven

The following pieces are now working together:

* GitHub Actions CI
* GitHub Actions OIDC authentication
* Restricted AWS IAM deployment role
* AWS Systems Manager
* EC2 deployment
* Private GitHub repository access through a dedicated SSH deploy key
* Exact commit deployment
* Locked dependency installation with `uv`
* Alembic production migrations
* systemd application restart
* Application health verification
* Automatic deployment from `main`

The important part is that these have been tested together through an actual deployment.

### What remains

The core deployment path is now done.

The next priority should not be adding more deployment machinery. Before introducing things like Docker, blue/green deployments, complicated rollback systems, or additional infrastructure, I want to make the existing deployment observable and reliable.

The next area to work on is therefore monitoring and operational visibility, especially:

* application/service logs
* EC2/system logs
* deployment failure visibility
* basic CloudWatch monitoring
* understanding how to diagnose a failed deployment or unhealthy application

After that, we can decide whether the project actually needs additional deployment features.

### Lesson from today

* The biggest lesson today was that a deployment pipeline is made up of several independent pieces, and getting one piece working does not prove the whole system works.

* We had AWS authentication working, SSM working, and GitHub access working, but the first real deployment still failed because the non-interactive SSM environment could not find `uv`.

* The useful part was not just fixing the error. It was tracing the failure through the actual deployment path instead of assuming the infrastructure was broken.

* The other important lesson was to keep the deployment simple.

We now have:

```text
GitHub Actions
    |
    v
AWS OIDC
    |
    v
SSM
    |
    v
EC2
```

That is enough for this project right now.

The goal is not to build the most sophisticated deployment platform possible. The goal is to have a deployment process that is secure, understandable, repeatable, and easy to troubleshoot.

Today, for the first time, a push to `main` can make its way all the way to the running production application automatically.

```

This is the point where I would consider the **deployment milestone complete**. The next milestone should be observability/operations, not more CI/CD complexity.
```
