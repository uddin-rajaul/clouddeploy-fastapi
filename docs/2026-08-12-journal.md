# Deployment Journal

## 2026-08-12 — CI/CD and AWS Deployment Access

Today I moved the project from having CI that only tests the code to actually preparing the deployment side of CI/CD.

The first part was getting GitHub Actions to authenticate with AWS properly. I did not want to put long-lived AWS access keys into GitHub, so we set up GitHub Actions OIDC with an IAM role instead.

There was a small but useful problem here. The trust policy initially used the repository subject I expected:

```text
repo:uddin-rajaul/clouddeploy-fastapi:environment:Production
```

but GitHub's actual OIDC token contained:

```text
repo:uddin-rajaul@110954532/clouddeploy-fastapi@1325005944:environment:Production
```

Once the trust policy was changed to match the real claim, GitHub Actions was able to assume the deployment role successfully.

This was a good reminder that IAM trust policies should be based on the identity AWS actually receives, not on assumptions about how GitHub formats it.

### AWS SSM deployment access

Instead of giving GitHub Actions direct SSH access to the EC2 server, I decided to use AWS Systems Manager (SSM) for the deployment connection.

The EC2 instance already has the SSM agent and the `AmazonSSMManagedInstanceCore` policy through its existing IAM role, so there was no need to introduce another service just to execute deployment commands.

A separate IAM role was created for GitHub Actions:

```text
clouddeploy-github-deploy-role
```

The role is trusted through GitHub's OIDC provider and restricted to the `Production` environment for this repository.

The deployment role was given permission to:

```text
ssm:SendCommand
ssm:GetCommandInvocation
```

The first SSM test failed because `GetCommandInvocation` had not been included. `SendCommand` itself had already worked and returned a command ID. After adding the missing permission, the complete test passed.

GitHub Actions successfully:

1. Assumed the AWS deployment role using OIDC.
2. Obtained temporary AWS credentials.
3. Sent an SSM command to the EC2 instance.
4. Waited for the command to finish.
5. Retrieved the command output.

The test returned:

```text
root
ip-10-0-1-82.ap-south-1.compute.internal
```

The command running as `root` is expected because SSM Run Command executes with elevated privileges by default. This does not mean the FastAPI application will run as root. The existing systemd service still runs the application as `ec2-user`.

### What is now proven

The AWS control path is working:

```text
GitHub Actions
      |
      | OIDC
      v
AWS STS
      |
      v
clouddeploy-github-deploy-role
      |
      | SSM
      v
EC2
```

This is a much better foundation than storing a personal AWS credential or GitHub token in the CI system.

### Important deployment decision still remaining

The actual application deployment has not been implemented yet.

The next question is how the private GitHub repository should be updated on EC2.

I do not want to go back to the original approach where EC2 manually authenticated to GitHub with a personal token. Since GitHub Actions can already reach EC2 through SSM, the deployment should be designed around that capability.

Before writing the final deployment script, I want to settle the repository-update mechanism and then define the deployment sequence clearly.

The intended deployment should eventually look roughly like:

```text
git push
   |
   v
GitHub Actions
   |
   | CI tests
   |
   | AWS OIDC
   v
AWS
   |
   | SSM
   v
EC2
   |
   +-- update application revision
   +-- uv sync --locked
   +-- alembic upgrade head
   +-- restart clouddeploy.service
   +-- verify service
   +-- verify HTTP endpoint
```

The important goal is not simply to make deployment work once. The goal is to make it repeatable while keeping the number of moving parts understandable.

### Lesson from today

The biggest lesson was that CI/CD is not just about writing a GitHub Actions YAML file.

There are several separate security boundaries involved:

* GitHub must prove its identity to AWS.
* AWS must decide exactly which GitHub workflow is trusted.
* The assumed IAM role must have only the permissions required for deployment.
* SSM must be able to execute commands on the intended EC2 instance.
* The deployment process itself still needs to be designed carefully.

The authentication and EC2 control path are now working. The next step is the actual application deployment.
